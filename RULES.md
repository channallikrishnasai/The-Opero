# OPERO — Engineering & Product Rules

| | |
|---|---|
| Document | RULES.md (3 of 6) |
| Status | **Permanent, binding.** Violations block merges. |
| Scope | Architecture · AI usage · Visual system · Assets · Data truth · Voice · Coding agents · Documentation |

These rules outlive any phase, feature, or deadline. When a new idea conflicts with a rule here, the rule wins until this document is deliberately amended in a reviewed commit.

---

## 1. Architecture rules

1. **Do not migrate OPERO to React.** The desktop UI is PyQt6 (`ui/`). React/TSX exists only for marketing pages (`aurora/`, `public/`, `site/`) and must never become the runtime UI. *(`pyproject.toml`, `ui/window.py`)*
2. **Do not introduce another 3D renderer.** No Spline, Unity, Unreal, Godot, Babylon, or second WebGL runtime. **Extend the existing Three.js renderer** (`site/web_background/index.html` + vendored `three.min.js`).
3. **Extend the existing Three.js renderer.** New visual capability = new commands/data flowing through `core/visual/bridge.py` → `window.operoVisual`, not a parallel scene.
4. **Keep the action system and the visual system separate.** Actions: dispatcher → safety → execution. Visuals: director/intent → world model → registry → bridge → scene. No shared execution path.
5. **Visualizations never authorize actions.** A rendered scene, an intent, or a visual result may not trigger, justify, or skip any action-system step.
6. **Safety gates remain authoritative.** `core/confirm.py` (UI-issued confirmation), `core/undo.py`, and validation run regardless of what the model, the visual system, or any caller claims.
7. **Prefer additive architecture over rewrites.** Extend existing modules; do not replace working subsystems to restyle them.
8. **Do not create duplicate systems.** Before building X, find the existing X: one tool registry, one dispatch, one confirmation gate, one memory store, one renderer, one voice gate (see `ARCHITECTURE.md`).
9. **Do not add dependencies without justification.** Check `pyproject.toml` first; state why nothing installed already solves the problem; avoid speculative pins.
10. **Verify repository state before changing architecture.** Read the actual code, tests, and git history first. Documentation and conversation memory are not proof (`RULES.md` §9 hierarchy).

## 2. AI rules (Gemini and any future model)

**Gemini MAY:**

- reason over context the app gives it;
- classify intent (answer / action / visualize);
- extract entities and arguments for tools;
- orchestrate multi-step workflows through **registered tools only**;
- generate a **structured `VisualIntent`** (validated dataclass: mode/action/camera/animation/targets/parameters).

**Gemini must NOT:**

- generate arbitrary Three.js / JavaScript / shader code — ever (`ARCHITECTURE.md` §12 boundary);
- invent physical object geometry and present it as authoritative truth — real objects come from registered, provenance-carrying assets;
- invent ISL signs or other authoritative factual displays (`PRD.md` §8);
- bypass or self-issue safety confirmations — it never sees a confirmation token;
- directly execute destructive operations — destructive acts require the UI confirmation path;
- write into memory categories marked safety-sensitive without explicit user action (`MEMORY.md` §9);
- treat its own prior outputs as evidence of external facts.

Model output is **untrusted input**: it is parsed, validated, and dispatched like any other external data.

## 3. Visual rules

1. **Face-first default.** The holographic face/core is the resting state; visualization is an exception granted by value (`PRD.md` §4).
2. **Visualization only when useful.** Apply the nine criteria in `PRD.md` §5; never visualize every noun.
3. **Real-world object rule.** Physical concepts render as recognisable real objects (correct proportions/materials) or fail with a structured message — never an arbitrary cube/sphere substitute (`PRD.md` §6).
4. **Semantic colors.** Follow the palette in `DESIGN.md` §6; color never carries meaning alone.
5. **Persistent entity IDs.** Deterministic IDs (`apple_01`) for the session; reuse, don't duplicate; never renumber live entities.
6. **Structured Visual Intent only.** Everything crossing into the visual runtime is a validated `VisualIntent` or its serialized dict — no free-form scene descriptions interpreted at render time.
7. **No arbitrary JavaScript generated by AI.** The Python→JS transport carries JSON data for a fixed command vocabulary (`ui/widgets.py::execute_visual`).
8. **Graceful fallback.** If WebEngine, WebGL, an asset, or the scene is unavailable, the app stays usable and reports a structured reason — never a blank window or a fake success.
9. **Accessibility.** Respect reduced motion, keyboard paths, readable labels, color-independent meaning (`DESIGN.md` §8).
10. **Performance limits.** Respect the ceilings in `DESIGN.md` §9: adaptive quality, lazy loading, cleanup of hidden objects, no unbounded scene growth.

## 4. Asset rules

- **Prefer GLB/GLTF.** The renderer loads GLB; other formats must be converted before registration, not at render time.
- **Every asset needs provenance.** `source` states where it came from (authored, downloaded, generated) with enough detail to retrace it.
- **Licensing must be documented.** No asset without a license string enters the registry; unknown license = not registerable.
- **Unverified assets cannot silently become authoritative.** `VERIFIED` is a separate, explicit state; existence ≠ verification (`core/visual/assets.py`).
- **Missing assets produce structured failures.** `missing_asset` / `unavailable` are valid outcomes; a placeholder primitive is not.
- **Never pretend an asset exists.** If the file isn't there, the record isn't AVAILABLE, and the user is told.
- **Path safety.** Project-relative paths only; absolute paths and `..` escapes are rejected at registration.

## 5. Data rules (never fabricate)

OPERO must never fabricate, in speech, text, memory, visuals, or logs:

| Category | Examples of forbidden fabrication |
|---|---|
| Prices / market data | "the stock is at $42" without a fetched source |
| Scientific facts | invented measurements, fake citations |
| Physical dimensions | object sizes not from the asset's own metadata |
| Medical anatomy | structures/functions not from a verified source |
| **ISL gestures** | sign forms not from an authoritative source (ISLRTC etc., `PRD.md` §8) |
| External datasets | rows, files, or records that were never loaded |
| Live information | news, weather, status not actually fetched this session |

Rules of operation:

1. Distinguish **fetched**, **remembered**, **inferred**, and **unknown** — label or hedge accordingly.
2. If a tool call failed, the answer is "I couldn't get it", not a plausible guess.
3. Visual demonstrations of factual content (anatomy, ISL, engineering) require provenance-carrying data; otherwise structured refusal.
4. Memory may only store what happened or what the user said — never synthesized "history" (`MEMORY.md` §6, §8).

## 6. Voice rules

The voice subsystem is governed by `core/voice_state.py` (**VoiceGate**) — one state machine, every path:

| Rule | Detail |
|---|---|
| States | Exactly `IDLE / LISTENING / THINKING / SPEAKING` (+ app-level `MUTED`, `SLEEPING` in the UI). All mic/transcript traffic consults the gate. |
| Speaking/listening exclusivity | TTS playback marks `begin_speaking()`; mic audio captured in that window is generation-stale and rejected. |
| Generation handling | Speech beginning bumps a generation counter; anything captured under an older generation is dropped — this is the TTS self-hearing loop kill-switch (`8b1408b`). |
| Echo prevention | Gemini-native mic, Gemini input transcriptions, and AssemblyAI finals all pass `accept_transcript` before being treated as user words. |
| Interruption | `interrupt()` = user barge-in: TTS stops, generations invalidate, control returns to listening. |
| Microphone lifecycle | Devices are opened/closed through the audio pipeline; mute is a state, not a cable pull; device changes go through `core/audio_devices.py`. |
| TTS lifecycle | One speaker path; visemes/mouth drive derive from the same stream the user hears — no mouth motion without audio. |
| Failure behavior | TTS/STT failure degrades to text/log — never a silent loop, never re-speaking its own output. |

## 7. Coding-agent rules

Every implementation phase (human or AI agent) must:

1. **Inspect current code first.** Read the modules the change touches; run `git status` / `git log`; never assume a previous report is accurate.
2. **Understand existing architecture.** Find the existing abstraction (`ARCHITECTURE.md`) before creating anything new; reuse over reinvent.
3. **Make minimal, additive changes.** Smallest diff that fully solves the problem; no drive-by refactors of unrelated files.
4. **Add tests.** Non-trivial logic leaves at least one runnable check that fails if the logic breaks.
5. **Run tests before claiming done.** `python -m pytest tests -q` — never claim a test passed if it didn't run.
6. **Run lint.** `ruff check . --select F821` (CI gate); full `ruff check .` when touching lint debt deliberately.
7. **Run formatting checks.** `ruff format --check .` on touched files at minimum; never reformat unrelated files to make a number go down.
8. **Report failures honestly.** Pre-existing failures are reported as pre-existing with evidence — not fixed silently, not hidden, not blamed on the change.
9. **Commit completed work.** One coherent commit per phase with a descriptive message (`feat(...)`, `fix(...)`, `docs: ...`, `test: ...`).
10. **Do not push unless explicitly requested.** Local commits only; pushing, rebasing, force operations, history rewrites, and branch deletions require explicit human instruction.

Banned tactics: disabling/skipping tests to pass CI, deleting failing assertions, inventing outputs, placeholder code presented as implementation, `git reset --hard` / force-push to "clean up".

## 8. Documentation rule

**Documentation must never become fiction.**

| State | Label to use |
|---|---|
| Implemented and verified in code | **CURRENT** (ideally with file/test reference) |
| Specified but not implemented | **PLANNED** |
| Implemented but rough / not validated | **EXPERIMENTAL** |
| Started but not usable | **INCOMPLETE** |
| Intentionally postponed | **DEFERRED** |

- Never describe PLANNED behavior in present tense.
- Never claim an API, file, dataset, model, or integration exists without repository evidence.
- When code and documents disagree, fix the document (or fix the code) in the same phase — record the discrepancy in `ARCHITECTURE.md` §16 until resolved.
- The six specification documents (`PRD`, `ARCHITECTURE`, `RULES`, `PHASES`, `DESIGN`, `MEMORY`) are updated **with** the phases that change reality, not after.

## 9. Source-of-truth hierarchy

When information conflicts, higher wins:

1. **Actual repository implementation** (code that runs)
2. **Tests** (executable expectations)
3. **Existing committed architecture/documentation**
4. **Current project specification** (these six documents)
5. **Planned roadmap** (`PHASES.md`)
6. **General assumptions** (incl. conversation summaries, memory recalls)

Never represent planned functionality as implemented — regardless of which level asserted it.
